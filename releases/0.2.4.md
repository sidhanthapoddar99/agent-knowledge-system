# 0.2.4 — a CLI verb is withdrawn, and the link gates stop guessing at markdown

**No content migration. `MIN_CONTENT_VERSION` stays at `0.2.0`.** Nothing on disk
needs changing; set `engine_version: "0.2.4"` in `site.yaml` when you upgrade.

Plugin: **`agent-ks` 0.8.0**. Update both together — most of this release is the
plugin.

## Breaking

**`agent-ks issue reindex` is gone.** It shipped in 0.2.3 and is withdrawn in the
next release, which is the shortest life any command here has had.

**The symptom:** `agent-ks issue reindex <id>` now exits `2` with *unknown
command*. If a script of yours calls it, delete the call — there is nothing to
replace it with, because the thing it maintained no longer exists.

**What it maintained, and why that went too.** 0.2.3 seeded a *generated* table
of an agent log's rounds at `02_working/00_index.md`, rebuilt from each round's
frontmatter, with a validator that compared the file against the generator and
errored on disagreement.

That validator could not work. The generator only read rounds stored as **files**;
a round stored as a folder — which the numbering has always allowed — was skipped
silently. The checker then asked the generator what the table *should* say,
inherited the same blind spot, and certified a table with a round missing.
Reproduced on real content: a table that ran `01, 02, 03, 05`.

> **Two things that make the same mistake cannot check each other.** That is the
> whole reason this was withdrawn rather than patched.

**What replaces it: nothing automatic.** `02_working/00_index.md` is still seeded
— an empty stub, so a fresh agent log still shows that it has three slots rather
than one — but you **write** it, one entry per round carrying *what that round
found*. That last part is the line worth reading, and no generator can produce it.

**Any `00_index.md` you already have keeps working.** It is a normal markdown
file now; nothing validates it and nothing overwrites it. Edit it freely — under
0.2.3 hand-edits were reverted by design.

**The `unit:` frontmatter field is no longer written** by `agent-ks issue
new-iteration`. It only ever existed to feed the generated table's *Kind* column.
No migration ships because the field lived entirely inside 0.2.3: if you have it
on a round file, `check issues` now reports it as an unknown key — delete the
line. The `--unit` **flag** is unchanged and still seeds `# Expected Outcome`.

## Fixed

**Every link gate was approximating markdown, and hiding broken links.** The four
tools that walk links — `check link-form`, `check skill-links`, `check issues`,
and `agent-ks move` — must ignore a link written inside backticks, because that
link is being *shown* rather than used. All four did that with hand-written
pattern matching, and it was wrong in ten ways that a real parser is not:

| Construction | What went wrong |
|---|---|
| a backslash-escaped backtick inside span content | a **real broken link** silently ignored |
| a blockquote, or a list inside one | same |
| a `===` setext underline | same |
| a GFM table with no leading pipes | same |
| an ordered list starting at `2.`, a lone `\|` line | a correctly-quoted link falsely reported |
| an indented code block, a raw HTML block | same |

**The four false negatives are the reason this is worth a release note.** A gate
that reports something is annoying; a gate that goes quiet is indistinguishable
from a clean tree, and you will act on it.

It now parses with `mdast-util-from-markdown` — **the same engine that renders
your site** — so the gate and the renderer cannot disagree about what a link is.

*If you have been relying on `check link-form` passing: re-run it.* On this
repo's own content the counts did not move, but yours may.

**`agent-ks move` was rewriting quoted examples.** It shared the same defect, and
it *writes*: a link inside a wrapped code span could be rewritten when its target
moved, editing a documentation example into something false.

**`check issues` skipped every run inside a grouping folder.** `new-agent-log
--group` nests runs under a folder of your choosing, and the validator warned
about that folder and then walked past it — so a malformed `settings.json`, a
missing `01_summary.md`, an invalid round status, colliding round numbers and the
depth cap were **all unchecked** for grouped runs. Demonstrated with the same
broken run in both places: ungrouped, one error; grouped, exit `0`.

*Expect new warnings after upgrading if you use `--group`.* They were always
true; nothing was looking.

## Changed

**The rule for when a run earns an agent log has one home and a stated default.**
It lived in fourteen places, which is fourteen chances to be stale; every copy is
now a link to
`references/20_sections/24_agent-logs.md → When an agent log opens at all`.

It also had a hole: work that is *repeated but independent* — a loop over thirty
unrelated subtasks — fired no trigger and hit no floor, so the rule returned
nothing and the answer came from an example instead. It now says **neither fires
→ ask, once per session.**

## Notes

**The plugin now imports four packages it does not declare** —`gray-matter` plus
three markdown ones — and ships no `package.json`. They resolve by walking up the
directory tree, which is reliable inside this repo and untested outside it. It is
tracked, and the first task on it is to reproduce the failure rather than assume
it.
