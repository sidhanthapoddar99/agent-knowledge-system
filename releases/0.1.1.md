# 0.1.1 — one lifecycle vocabulary: seven statuses, four categories, one field name

Issues and subtasks stop having separate lifecycle fields. Subtask `state:`
becomes `status:` — the name issues already used — and the four values
`open | review | closed | cancelled` become **seven statuses grouped into four
categories**, declared once in framework code and shared by the loader, the UI,
the CLI and the validator. A tracker can no longer invent its own statuses, and
an unrecognised status is now a hard startup error instead of quietly becoming
`open`.

**This release does not stop your build, and that is the problem with skipping
it.** The engine still reads the old field name and the old values, mapping them
on the fly with a warning — so an un-migrated tree renders correctly while what
is written on disk drifts steadily away from what everything reports.

**Engine `0.1.1` · floor n/a · plugin `0.4.0`** — released 2026-07-02, tag `v0.1.1`.

## Breaking changes

| What changed | The symptom if you skip it | Fix |
|---|---|---|
| **Subtask field renamed `state:` → `status:`** | One warning per file: *"uses the legacy `state:` field — run the state→status migration"*. Then it gets worse rather than better: the CLI and the editor's subtask toggle now **write `status:`**, and the writer appends the key rather than replacing `state:`. So the first time a subtask is flipped it ends up carrying **both lines**, `status:` silently wins, and the stale `state:` line stays behind reading as the file's status to any human or agent who opens it | `migration/0.1.1_state-to-status.py` |
| **Terminal values renamed** — `closed` → `done`, `cancelled` → `dropped`, on issues and subtasks alike | Mapped on read with a warning per occurrence, so pages look right. But the value on disk stops matching the value everything reports, `agent-ks check issues` flags every one, and anything reading the raw frontmatter — a grep, a script, an agent — reads a word the vocabulary no longer contains | same script |
| **Statuses are fixed in framework code.** A tracker's `fields.status.values` list is no longer consulted for validity | The list is ignored rather than refused, so it keeps reading as authoritative while doing nothing. Any file using a value outside the seven **and** outside the legacy map now fails at startup with `[issues] Invalid lifecycle status "<value>" in <file>` — build and dev alike | no script — remove the invented statuses, or map each onto one of the seven by hand. (The `fields.status` block becomes a hard error one version later, in `0.1.2`) |
| **The silent default-to-open is gone.** An unparseable status used to become `open` with nothing said | Same hard error. This is the intended direction — a typo that used to hide as "open" now names itself — but it means a tree that loaded before may refuse to load now | — |
| **Plugin side: the flat `docs-*` command shims were retired** for a single `docs-guide <group> <verb>` dispatcher (2026-06-23, plugin `0.3.0`). The bare `docs` name went too — it collided with a `docs/` directory on `PATH` | Every `docs-list` / `docs-set-state` / `docs-check-*` invocation fails with command-not-found. The old names survive only as internal ids, so `docs-guide help docs-list` still resolves | no script — update the call sites. Note this dispatcher was itself renamed `agent-ks` on 2026-07-08 |

## Upgrade

Both scripts take a path — a single file, one issue folder, or a whole tracker.
From the framework root, ascending:

```bash
# if you are coming from a pre-0.1.0 tree, run this one first
python3 migration/0.1.0_done-to-state.py  detect  <content-root>
python3 migration/0.1.0_done-to-state.py  migrate <content-root> --dry-run
python3 migration/0.1.0_done-to-state.py  migrate <content-root>

python3 migration/0.1.1_state-to-status.py detect  <content-root>
python3 migration/0.1.1_state-to-status.py migrate <content-root> --dry-run
python3 migration/0.1.1_state-to-status.py migrate <content-root>

# exits 1 while any legacy field or value remains
python3 migration/0.1.1_state-to-status.py verify  <content-root>
```

There is no `site.yaml` step. `engine_version` does not exist until **0.1.2**,
where the version gate ships — so nothing on disk records that a tree has
reached 0.1.1, and the version to declare is the one at the end of whatever
chain you are running.

What the script touches: subtask frontmatter under any `subtasks/` directory
(rename the field, remap the value), and the top-level `status` in each issue's
`settings.json` / `settings.jsonc`. Where both `status:` and `state:` are
present, `status` wins and `state:` is dropped. Agent-log `status:` fields,
notes and comments are left alone — agent-log status was a different, free-form
field at this point and never carried these values.

## What's new

- **Seven statuses, four categories.** `open` and `blocked` are Not Started;
  `in-progress` is In Progress; `input-needed` and `review` are Review;
  `done` and `dropped` are Closed. The category is always derived from the
  status and never written to a file. Transitions are not enforced — any jump
  is legal, and the ordering is guidance.
- **The two Review statuses say *why* a human is needed** — `input-needed` for
  an agent stuck on a question it wrote into the file itself, `review` for work
  finished and awaiting sign-off. `blocked` is reserved for a structural
  dependency on another item and deliberately does **not** promote an issue into
  the review queue; it rests, and its reason is read in place.
- **One exported constant** declares the statuses, their category grouping and
  their default colours. The loader, the layouts, the detail-page guide panel
  and the CLI all consume it — ending a three-way drift where the loader type,
  the CLI library and the validator each hardcoded their own list.
- **Filter tabs are the four categories, not the seven statuses**, with the
  status kept visible as a coloured badge on every row and card. Review-debt is
  computed from the Review category.
- **The issue-anatomy restructure** (2026-07-01 → 07-02) — `brainstorm/` for
  deliberation that converges on a decision, `agent-memory/` for what an issue
  has settled, an optional glossary panel, agent-log kinds (`lp` loop, `au`
  audit, `rf` refactor, `it` iteration, `wf` workflow — each with a name and an
  icon, extendable per issue), a per-issue guide panel, site-wide tooltips, and
  done/total counts on subtask folders.
- **Issue-creation threshold rules** — what earns a full issue folder, what is
  a subtask on an existing issue, and what is a brainstorm entry. Shipped with
  a quick-idea-capture slash command so a half-formed thought has somewhere to
  go that is not a new folder.
- **Tracker settings may be JSONC.** A sibling `settings.jsonc` is preferred
  over `settings.json`, so comments and trailing commas survive — which is what
  makes a hand-authored vocabulary readable.
- **One CLI entrypoint** — `docs-guide <group> <verb>`, with a grouped listing
  on bare invocation, a cross-content `find`, a `git` content helper, and a
  self-test harness.
- **Content images go through a shared asset-src post-processor**, so an image
  path resolves the same way from every content type.

## Fixed

- **`set-state --subtask` silently flipped the wrong thing.** The flag was
  ignored and the *issue's* status got set instead of the subtask's. It now
  resolves the file by number or slug, and an unresolvable `--subtask` errors
  rather than falling through to the issue.
- **Wide tables no longer overflow their column** — rendered tables are wrapped
  for horizontal scroll.

## Notes

- **The version number was assigned retroactively**, on 2026-07-03, when the
  engine↔content version contract was designed. This work shipped under no
  version at all; the script was `2026-07-02_state-to-status.py` inside the
  plugin, renamed `0.6.0_…` and then `0.1.1_…` the same day the contract landed.
- **The window this note covers** is the commits between the 0.1.0 anchor
  (2026-06-22) and the 0.1.1 anchor (2026-07-02). It is not an exhaustive
  changelog of those eleven days — the format change is complete, the feature
  list is the consumer-visible subset.
- **The plugin version moved four times inside this window** (`0.2.1` → `0.4.0`
  at the anchor commit, reaching `0.6.0` by the end of the same night as the
  lifecycle model propagated into the skills and the CLI). `0.4.0` is what the
  anchor commit carries; a consumer taking this release in practice took a
  later plugin.
- **In-progress used to be derived from `assignees.length > 0`.** That
  derivation is removed, and with it every document that described assignees as
  the in-progress signal. This was a deliberate policy reversal of the earlier
  "transient state is a label, not a status" doctrine, taken because the
  derivation never matched how the tracker was actually used.
- **No status is inferred from a label.** The `wip` and `blocked` labels are
  kept and deprecated in place rather than stripped — statuses start honest, and
  a label that once meant "in progress" is not evidence that it still does.
  (Both labels are retired in `0.2.0`.)
- **`state:` is still tolerated today**, three versions later, with the same
  warning. The compatibility read has never been removed, so an un-migrated tree
  keeps limping rather than failing — which is exactly why the drift described
  in the first breaking change is the symptom that matters.
- **The script's own USAGE block named the file `2026-07-02_state-to-status.py`**
  — its pre-rename name — so copy-pasting from the docstring failed on a
  file-not-found. Corrected in `0.2.0`, after this note surfaced it. An older
  checkout still has the wrong name; use the `0.1.1_` name it ships under.
- **Could not be determined:** whether any tracker outside this repo carried a
  custom `fields.status.values` list, and therefore whether the "statuses are
  fixed in code" change broke a real tree or only a theoretical one. Nothing in
  the history records a consumer hitting it.
