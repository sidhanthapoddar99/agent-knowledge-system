# 0.2.2 — a URL written against the file tree now resolves

**No content migration. Nothing to do on upgrade.** `MIN_CONTENT_VERSION` stays
at **0.2.0**; content written for 0.2.0 needs no change. Every fix here is in the
router, and every one of them makes a URL that used to fail start working — none
takes one away.

Plugin: **`agent-ks` 0.7.2**. Update both together.

This release exists because of a diagnosis that was wrong for a week, and the
correction is the most useful thing in it — see *Notes*.

## Upgrade

Nothing. Bump the engine, reinstall the plugin.

## What's new

### Docs and blog accept both URL spellings

Docs strip `NN_` ordering prefixes from their URLs and blog strips the date
prefix, so a link that named a file by its **real path on disk** — the form this
project requires — landed on a page that did not exist.

Both spellings resolve now. The clean slug stays canonical and the source form
redirects to it, so there is still exactly one URL to write down:

```
/user-guide/19_issues/01_overview   →  302  →  /user-guide/issues/overview
/blog/2024-01-15-hello-world        →  302  →  /blog/hello-world
```

The match is made against the file, not by stripping prefixes from the URL and
retrying: every content item carries its own path, so the lookup is exact and
cannot drift out of step with the slug transform.

### Any file under a plan resolves to the plan

A plan folder renders as one page, so `overview.md` — the plan's own body — had
no URL of its own and a link to it was a 404. It now redirects to the plan.
Stage files already redirected to their anchor; that is unchanged.

### `agent-ks --version`

Prints the plugin version **and the directory it ran from**:

```
$ agent-ks --version
agent-ks 0.7.2
/home/you/.claude/plugins/cache/…/agent-ks/0.7.2
```

The path is the useful half. If you also have a framework checkout, the same
version number can sit on two different trees, and the path is the only thing
that tells you which copy answered.

## Fixed

**A missing page answered `200`.** A URL inside a section that named no document
rendered the *Page Not Found* body with an HTTP `200` status. Any link checker
that trusts the status code — which is the obvious way to write one — reported
dead links as healthy.

It now answers **`404`**, and still renders the same styled page. If you have a
link checker that was passing, expect it to start finding things. That is the
point.

**`agent-ks check skill-links` could still read the wrong tree.** 0.2.1 fixed it
by walking up from the current directory to find a plugin source tree. That guess
fails in consumer mode, where the framework clone sits *inside* your project and
is exactly what you are standing in — so the walk-up found the framework's
bundled skills and labelled them authoritative.

The walk-up is gone. The script resolves from its own location, so **the command
you type states which tree you mean**, and the banner names it.

## Notes

**Two independent reviews agreed on a finding that was wrong, and the agreement
is what made it convincing.** Both concluded that relative links between tracker
pages resolve one level too deep and 404 en masse; one measured 1,410 failures.
Fifteen links were then opened by hand and twelve worked.

Both reviewers had read the **built** site. A built page is a directory served
with a trailing slash; the dev server serves the same page without one. That one
segment changes what every relative link means — so `dist/` cannot answer the
question at all, and neither reviewer had made a request.

Two consequences worth carrying:

- **A finding measured in one environment is not a finding about the other.**
  Name which one you measured in.
- **Two methods that share an assumption are one method.** Independence is about
  what a check reads, not who ran it.

**The 0.2.1 note carries a third dated correction** for the claim above, added
here. It already carried two.
