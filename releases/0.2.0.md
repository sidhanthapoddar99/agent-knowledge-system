# 0.2.0 — plans, one status vocabulary, and an agent log that reads in order

The tracker gains a **plans section**: ordered stages with their own status,
owner and outcome, so a body of work has a live plan alongside its subtasks. The
status vocabulary is now **one set of seven, shared by issues, subtasks, plan
stages, agent logs and iteration files** — there is no second vocabulary to
learn. Status colours move from tracker settings into theme CSS, and an agent
log's three slots are numbered so its reading order is stated in the filenames.

**This release forces action.** Every change to the content format is breaking,
so the floor is raised to match the engine and 0.1.x content is stopped at
startup until it is migrated.

**Engine `0.2.0` · floor `0.2.0` · plugin `0.7.0`**

## Breaking changes

| What changed | The symptom if you skip it | Fix |
|---|---|---|
| **Agent-log status vocabulary** — fourteen accepted aliases (`todo`, `wip`, `success`, `failed`, …) collapse to the canonical seven | Ten of the fourteen stop validating. `agent-ks check issues` errors on every agent-log file that uses one, and the status chip renders empty | `migration/0.2.0_agent-log-status-vocabulary.py` |
| **`iteration:` frontmatter dropped** from agent-log files | Silently ignored — nothing renders it. The `NNN_` filename owns the number now | same script |
| **`wip` / `blocked` labels retired** from tracker vocabularies | The label stays in `settings.json` and keeps being offered, though execution state is a status now | same script |
| **`statusColors` removed from tracker settings** — status colours are theme CSS variables (`--status-<name>`) | **Hard error at load.** The key is refused rather than ignored, because ignoring it would silently drop a palette someone deliberately set | `migration/0.2.0_status-colors-to-css.py` |
| **Agent-log slots numbered** — `summary.md` → `01_summary.md`, `working/` → `02_working/`, `debrief/` → `03_debrief/`; a folder prefixed `100` or above is a child run, not a slot | The reader finds no summary and the run shows as an unstructured pile of files. Inbound links still point at the old names | `migration/0.2.0_agent-log-slot-numbering.py` (renames **and** rewrites every inbound link) |

**The floor equals the engine on purpose.** None of the above degrades
gracefully — each one misreads rather than declines — so there is no version
between `0.1.2` and `0.2.0` that content should be allowed to sit at.

## Upgrade

Your build will stop with the version error naming your current version and
`0.2.0`. From the framework root:

```bash
# 1. Every script in (your-version, 0.2.0], ascending. A zero-hit detect is a
#    passed check, not a script you were allowed to skip.
python3 migration/0.2.0_agent-log-status-vocabulary.py detect  <content-root>
python3 migration/0.2.0_agent-log-status-vocabulary.py migrate <content-root> --dry-run
python3 migration/0.2.0_agent-log-status-vocabulary.py migrate <content-root>

python3 migration/0.2.0_status-colors-to-css.py detect  --root <project-root>
python3 migration/0.2.0_status-colors-to-css.py migrate --root <project-root>

python3 migration/0.2.0_agent-log-slot-numbering.py detect  --root <content-root>
python3 migration/0.2.0_agent-log-slot-numbering.py migrate --root <content-root> --dry-run
python3 migration/0.2.0_agent-log-slot-numbering.py migrate --root <content-root>

# 2. Verify
agent-ks check issues
python3 migration/0.2.0_agent-log-slot-numbering.py verify --root <content-root>

# 3. LAST — and only now
#    site.yaml:  engine_version: "0.2.0"
```

Bumping `engine_version` before running the chain defeats the gate's whole
purpose: it tells the engine the content is migrated when it is not, and moves
the breakage somewhere nothing points at it.

**Older than `0.1.2`?** Run the earlier scripts in the range too — `0.1.0`,
`0.1.1` and both `0.1.2` scripts — in version order, before the three above.

**Your history stays as written.** The slot-numbering script skips agent-log
folders in the retired six-slot shape (`00_goal.md` … `05_notes.md`) rather than
half-converting them, and reports each one it skipped.

## What's new

- **Plans** — `plans/NN_<name>/` with an overview and ordered stages. Each stage
  carries status, owner, outcome and notes, and links the subtasks it executes
  against. The highest-numbered plan is the active one; one plan open at a time.
  CLI: `agent-ks issue new-plan`, `agent-ks issue new-stage`.
- **One status vocabulary everywhere** — the canonical seven, fixed in framework
  code and shared by every file kind. On an agent log, `status` answers *did the
  agent finish its assignment*, not *was the news good*: an audit that completed
  and found five defects is `done`. What it found belongs in the file's
  `# Outcome`.
- **Numbered agent-log slots** — `01_summary.md` / `02_working/` / `03_debrief/`,
  so the reading order is in the filenames. A child run is any folder prefixed
  `100` or above. `agent-ks issue new-iteration` opens a round's file with its
  head pre-filled.
- **Status colours in theme CSS** — one `--status-<name>` variable per status,
  which lets light and dark differ. The JSON map could not.
- **Ordering labels in links** — link text may open with the target's ordering
  path (`[040/100 name](path)`); `agent-ks move` rewrites it, and the validator
  warns when it drifts.
- **CLI additions** — `issue new-plan`, `issue new-stage`, `issue new-iteration`,
  `issue new-subtask`, `check legacy-tags`, `theme tokens`. Run `agent-ks help`
  for the current list.

## Fixed

- **The version gate had never once fired on a migrated format.**
  `compareFormatVersions` compared only the first two places and discarded the
  third — and every migration this project had shipped moved the third, so
  content at `0.1.0` compared *equal* to a floor of `0.1.2` and passed. The only
  thing the gate ever caught was content with no `engine_version` at all. It now
  compares all three, which is what makes this release's floor mean anything.
- **The plans validator accepted an agent-log file as a `subtasks:` target** —
  the renderer resolves against subtasks alone, so such a stage passed the gate
  and then drew "resolves to nothing" on its own page. The two failure modes now
  give different messages.
- **One stray filename could silence every agent-log rule on a valid run.** The
  retired-shape detector skipped the whole folder, and the skip reported
  nothing, so silence and clean were the same output.
- **`agent-ks` no longer claims to run under node.** The scripts import
  `gray-matter`, which node cannot resolve here; the dispatcher now refuses with
  an install hint instead of dying on a module-resolution stack trace.
- **A one-digit ordering prefix** could pass validation while making the wrong
  plan active — the validator and the loader now share one parser.

## Notes

- **The three migrations are all named `0.2.0_*`,** including two drafted as
  `0.1.3` and one as `0.1.4` before this release landed on `0.2.0`. No engine
  ever existed at those numbers, so no content could legitimately declare one.
  Scripts sharing a version have no defined execution order between them, so
  they are written to be order-independent — each walks the tree itself rather
  than consuming a list another produced.
- **The plugin's advertised command count was removed rather than corrected.**
  It said 29, `agent-ks help` listed 35, and the marketplace copy said 28. The
  description now points at `agent-ks help` for the live list.
- **No backfill of ordering labels onto existing links** — deliberate. New and
  edited links carry them; old ones are left alone.
