# 0.2.1 — three gates that were passing things they should have refused

**No content migration. Nothing to do on upgrade** — unless your `site.yaml`
registers a page whose data folder does not exist, in which case the build will
now tell you instead of quietly rendering an empty section. See *Breaking* below.

`MIN_CONTENT_VERSION` stays at **0.2.0**, and this is the first release where the
floor and the engine version differ. That is the floor working as designed: it
means *oldest content that still loads*, not *newest release available*. Content
written for 0.2.0 needs no change.

## Breaking

**A page whose `data` path does not exist is now a startup error.**

`loadSiteConfig()` refuses any `pages.*.data` that resolves to a missing path,
naming the alias as written, the resolved absolute path, and the `site.yaml` key
— and it reports every offender at once rather than failing on the first.

If your build passes today, this changes nothing. If it fails, the entry was
already broken and rendering an **empty section**: no error, no warning, and no
visual difference from a section whose content you deleted on purpose. That is
the whole reason it is now a refusal — the failure looked exactly like success.

Fix either way: create the directory, or delete the entry from `pages:`.

> The check is **existence only**, not "is a directory". A section page points at
> a folder, but a single-page type points at one YAML file
> (`pages.home.data: "@data/pages/home.yaml"`), and both are valid.

## Fixed

**`agent-ks check skill-links` was checking the installed plugin, never your
working tree.** It resolved its scan root from its own location on disk, and the
`agent-ks` dispatcher on `PATH` *is* the installed plugin — so a bare run scanned
`~/.claude/plugins/cache/…` and reported a clean pass over files it had not read.
It now walks up from the current directory to find a plugin source tree, falls
back to the installed copy **with a warning**, and names which tree it read in
the banner.

*If you develop this plugin, every previous "skill-links clean" you recorded
describes the installed copy rather than what you committed. Re-run it.*

> [!IMPORTANT]
> **Correction, 2026-08-03 — the walk-up described above was replaced the same
> week.** It moved the wrong-tree bug rather than removing it: in **consumer
> mode** the framework clone sits *inside* your project, so standing in it made
> the checker scan the **bundled** skills and label them `[source tree]` — not the
> plugin you actually have installed.
>
> There is no filesystem test that separates "maintaining the plugin" from
> "sitting in your framework folder", because those are the same directory. So
> the anchor is now the command you type, not where you stand:
>
> | Command | Always scans |

> | `agent-ks` | the installed plugin |
> | `agent-ks-dev` | this repo's source tree (maintainers only) |
>
> **Nothing to do as a consumer** — `agent-ks` now reliably reports on the copy
> you run, which is what you wanted from it. The banner still names the tree.
> Shipped in the next release; see
> `2026-08-02-refactor-efficiency-and-planning/subtasks/090_silent-failure-defects/040_two-commands-not-one-guess.md`.

**The agent-log numbering lint missed two cases it was written to catch.** A
single producer file with no iteration file passed, because the guard required
more than one (`list.length > 1`) — the more likely mistake of the two, since it
is what an agent produces when it writes one artifact and never writes the round
up. And nothing at all caught two files ending `0` in the same iteration, both
claiming to be that round's own record. Both now warn.

## Added

**`0.2.0_agent-log-status-vocabulary.py` reports iteration-number
disagreements before dropping the field.** That migration is the only moment
both the filename prefix and the `iteration:` frontmatter value exist; afterwards
the field is gone and a disagreement is not merely hard to find, it is gone. The
detect pass now reports any file whose prefix and field contradict each other,
**keeps the filename, and changes nothing else** — renaming to match a value we
just decided was untrustworthy would trust the wrong half, and a rename breaks
every inbound link.

> **It only compares files in the current `02_working/` shape, and that
> restriction is the finding.** Run across every agent-log file, the comparison
> reports 83 disagreements out of 83 in this repo's own pre-migration history —
> all false. In the retired shape the two numbers were never two copies of one
> fact: `MNN_` counted **milestones** and `iteration:` counted **rounds**, so a
> file numbered `102_` inside round 1 was correct. Only in the new shape do the
> prefix and the field claim the same thing, and only there can they contradict.

## Bundled user guide

**Every relative link in the issues user guide was a 404 — all 85 of them.**
Pages build as `<slug>/index.html`, so every page URL ends in a slash, and
`./sub-docs/plans` from `/user-guide/issues/design-philosophy/` resolved to
`…/design-philosophy/sub-docs/plans`. Writing a correct relative link meant
counting `../` against a URL depth that is not visible in the source tree, and
not one of 101 links got it right.

All 101 are now root-relative. The section reads 210 links checked, 0 broken.

> The rest of the site is **not** fixed and the numbers are worse: 243 broken in
> the wider user guide, 70 in dev-docs. Nothing checks links inside content — the
> skill-file link checker covers `plugins/` only. A content link checker, and the
> sweep, are tracked and not in this release.

> [!CAUTION]
> **Correction, 2026-08-03 — the diagnosis in this section was wrong, and the fix
> it describes has been reverted.**
>
> **The measurements above are all still true.** 85 links were 404ing; not one of
> 101 got it right. What was wrong is what that was blamed on.
>
> *"Not one of 101 links got it right"* is evidence about the **tool**, not the
> authors — 101 links written independently and all failing identically is what a
> broken transform looks like. The authors had counted correctly. The renderer
> (`src/parsers/postprocessors/internal-links.ts`, 81 lines) emitted the `./`
> prefix unchanged while every page builds one directory deeper than its source
> file. It was opened for the first time *after* this note was published.
>
> **Why the "fix" was worse than the bug.** `agent-ks move` skips every link
> target starting with `/`, so all 341 converted links had silently left link
> maintenance and would have rotted on the next file move — with nothing
> reporting it. The conversion was reverted in `ee404bb`.
>
> **What actually fixed it:** a one-level URL-depth shift in the renderer, index
> pages exempt. Control-tested both directions — **418 broken in-body links with
> the shift disabled, 0 with it enabled**, over the same 173 pages and 15,585
> links, with **zero content files changed**. Shipping in the next release.
>
> **If you are reading this note alone: do not convert relative links to
> site-absolute form.** That is the mistake this block exists to retract.

> [!CAUTION]
> **Correction, 2026-08-03 (third on this note) — the depth-shift claim above is
> narrower than it reads, and it does not hold everywhere.**
>
> *"418 broken in-body links with the shift disabled, 0 with it enabled"* was
> measured against the **built** site, and is true there. It is **wrong on the
> dev server**, which serves the same page without a trailing slash — so the
> shift over-corrects and a docs link lands one level too shallow. A single
> constant offset cannot be right in two environments that differ by one URL
> segment.
>
> Two of the numbers in that sentence are also wrong in kind: `15,585 links`
> counts repeated sidebars (the real in-body figure is ~569), and `0 broken`
> means **0 broken paths** — fragments were never checked, and four broken
> anchors existed at the time.
>
> A separate claim recorded during that work — that relative links between
> tracker pages 404 en masse, measured at 1,410 — **is retracted outright.**
> Twelve of fifteen links opened by hand resolved correctly. Tracker pages are
> served without a trailing slash and keep their `NN_` prefixes, so a relative
> link written against the file tree already lands where the author meant.
>
> **What to do about it: nothing, if you are on 0.2.2.** That release fixes the
> URLs this misdiagnosis was chasing, in the router rather than in your content.
> The instruction from the block above still stands unchanged and is the one to
> keep: **do not convert relative links to site-absolute form.**

## Plugin

`agent-ks` **0.7.1** — the audit follow-ups: one home for who may close an agent
log, a stage-status section for `plans/`, the worked examples migrated off the
retired model, and the guide page for using the tracker with an AI rewritten
against reality with every command executed rather than transcribed.

Two documentation claims were disproved by measurement rather than argument:
a missing frontmatter `title` does **not** fail the build (it falls back to the
slug, silently), and child agent logs nest **two** levels rather than one — which
is what the validator and CLI already enforced and said in as many words.
