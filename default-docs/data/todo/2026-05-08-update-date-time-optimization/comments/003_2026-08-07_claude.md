# The module-isolation cause is fixed at the root. The watcher half is not.

The Astro 7 work touched this issue's territory without meaning to. Splitting what
changed from what did not, because the two halves have opposite answers.

## Fixed — the two-caches cause, at the root rather than around it

[`notes/03_ssr-module-isolation.md`](../notes/03_ssr-module-isolation.md) describes
the plugin context and the SSR context holding **separate instances** of
`issue-dates.ts`, each with its own `cache` Map, so `invalidateIssueDateCache()`
cleared a copy no render ever reads.

**Reproduced, by counting module instantiations in one dev server:** instance #1 at
boot, instance #2 on the first request, both alive at once. The note is right.

The caches in `issue-dates.ts` (`cache` and `repoRootByPath`) and in `issues.ts`
now live on `globalThis`, matching the pattern `paths.ts` and `cache.ts` already
used. **One state object, both contexts.** Commit `033c5ff`.

So the `moduleGraph.invalidateModule` workaround this issue introduced no longer
has a reason to exist. It has **not** been removed — see below for why.

Also fixed on the way: `invalidateIssuesCache(dataPath)` deleted a bare
`dataPath` while entries are keyed `<dataPath>::<flags>`, so the targeted form
matched nothing and only the clear-everything form ever worked.

## NOT fixed — the watcher does not appear to fire

🔴 **A commit made with the dev server running produced no watcher output at all.**
Not `git ref changed`, not `SSR module invalidated`, not the `no SSR modules in
graph yet` fallback — none of the three messages the handler can print.

The paths *are* registered; the boot log shows both `.git/HEAD` and the branch ref.
So it is armed and silent.

**This matters more here than anywhere else**, because `ensureFresh()` in
`issue-dates.ts` is deliberately lazy: it returns immediately whenever the cache is
populated and never re-checks git. The watcher is the *only* thing that can make a
date refresh. If it never fires, no amount of cache-sharing helps — the entry is
simply never cleared.

**Not confirmed as an Astro 7 regression.** The same watcher could not be made to
fire on Astro 5 either, so there is no control. That test is
[its own subtask now](../../2026-08-07-astro-7-and-load-time-refactor/subtasks/060_followups/010_git-ref-watcher-is-silent.md).

## Why the `moduleGraph` reach-in stays for now

Its reason for existing is gone, but it **only ever runs inside the silent
handler**. Deleting 25 lines of code that cannot be observed running is not a safe
cleanup. Settle the watcher first; that subtask says the same.

## What this means for this issue's own scope

This issue is about **scaling** — cold rebuild at 3K+ issues. None of that changed,
and its three subtasks are untouched.

But [`01_eager-incremental-refresh`](../subtasks/01_eager-incremental-refresh.md)
now has a second reason to exist. It was ranked as a performance optimisation; if
the watcher really is unreliable, an incremental refresh that does not depend on a
file watcher is also the **correctness** answer, not just the fast one. Worth
re-reading it with that in mind before picking an order.
