# 0.1.2 — the version contract: content declares what engine it was written for

This is the release that made the previous two nameable. Content now declares
`engine_version:` in `site.yaml`, the engine carries its own version and a
compatibility floor, and `loadSiteConfig()` refuses to start when the two are
out of range — in both directions, with a message that walks an AI through the
migration chain. Migrations move out of the plugin and into `migration/` at the
repo root, named by the version they bring content **to**, so they ship in the
same clone as the engine that needs them.

Two format changes ride along, both of them hard errors: the tracker root's
`settings.json(c)` gets a new vocabulary schema, and the retired custom-tag
syntaxes get a converter.

**This release forces action** on every tree, including trees that need no
content change at all — a `site.yaml` with no `engine_version` is treated as
`0.0.0` and refused.

**Engine `0.1.2` · floor `0.1.2` · plugin `0.5.2`** — released 2026-07-03, tag `v0.1.2`.

> **Reconstructed from git history on 2026-08-03.** No note was written and no
> tag was cut at the time — see Notes for how the anchor commit was derived.
> This is the first version `ENGINE_VERSION` actually held; `0.1.0` and `0.1.1`

## Breaking changes

| What changed | The symptom if you skip it | Fix |
|---|---|---|
| **`site.yaml` gains `engine_version:`** (top-level, sibling of `theme`). A tree that does not declare one is read as `0.0.0`, and the floor is `0.1.2` | **Dev, build and preview all stop** in `loadSiteConfig()`: *"This content targets engine 0.0.0 (no engine_version declared in site.yaml), but this engine is 0.1.2 and supports content 0.1.2 or newer…"* — followed by the full migration runbook | run the chain below, then add `engine_version: "0.1.2"` as the **last** step |
| **Tracker root `settings.json(c)` may no longer declare a `fields.status` block.** Statuses were fixed in code in `0.1.1`; ignoring the block was the bug, so it is now refused | **Hard error during `getStaticPaths`** — the build aborts with *"declares `fields.status`, but statuses are fixed by the framework and cannot be defined per-tracker. Fix: delete the entire `fields.status` block…"*. `agent-ks check issues` reports the same, exit 1, without a build | `migration/0.1.2_root-settings-schema.py` (facet A) |
| **Every `component` and `labels` value must carry an entry in a parallel `descriptions` map.** These render in the tracker Guide modal, so a missing one is a visible hole | **Hard error at load**, naming the offenders: *"every `component` value must declare a description (these are rendered in the tracker Guide). Missing for: `<values>`"*. `priority` descriptions stay optional | same script (facet B) |
| **Status colours move to a top-level `statusColors` map**, a sibling of `fields` rather than a child of `fields.status`. Keys are validated against the seven statuses | A colour key for a status that does not exist is a typo, and is now a hard error rather than a silently dropped entry | same script — its `guide` command prints the paste-in replacement |
| **The custom-tag syntaxes are retired outright.** `:::callout` / `:::collapsible` / `:::tabs` and the `<callout>` / `<collapsible>` / `<tabs>` / `<tab>` tag forms are gone, and so is the dormant transformer code that might one day have parsed them | The directives **render as raw text in the page** — literally `:::callout{type="info"}` on screen. Nothing errors and nothing warns, because the engine never parsed them in the first place; deleting the transformers only closed the door on them ever working | `migration/0.1.2_legacy-custom-tags.py` |

## Upgrade

Your build will stop with the version error naming your current version and
`0.1.2`. Run every script in `(your-version, 0.1.2]`, ascending — a zero-hit
detect is a passed check, not a script you were allowed to skip. From the
framework root:

```bash
# 1. Earlier links of the chain, if your tree predates them
python3 migration/0.1.0_done-to-state.py   detect  <content-root>
python3 migration/0.1.0_done-to-state.py   migrate <content-root> --dry-run
python3 migration/0.1.0_done-to-state.py   migrate <content-root>

python3 migration/0.1.1_state-to-status.py detect  <content-root>
python3 migration/0.1.1_state-to-status.py migrate <content-root> --dry-run
python3 migration/0.1.1_state-to-status.py migrate <content-root>
python3 migration/0.1.1_state-to-status.py verify  <content-root>

# 2. Tracker-root vocabulary schema — DETECTION ONLY, you paste the result
python3 migration/0.1.2_root-settings-schema.py detect <tracker-root>
python3 migration/0.1.2_root-settings-schema.py guide  <tracker-root>
#    …apply the printed replacement by hand, then:
python3 migration/0.1.2_root-settings-schema.py verify <tracker-root>

# 3. Retired custom-tag syntax
python3 migration/0.1.2_legacy-custom-tags.py detect  <content-root>
python3 migration/0.1.2_legacy-custom-tags.py migrate <content-root> --dry-run
python3 migration/0.1.2_legacy-custom-tags.py migrate <content-root>

# 4. Verify
agent-ks check issues

# 5. LAST — and only now
#    site.yaml:  engine_version: "0.1.2"
```

Bumping `engine_version` before running the chain defeats the gate's whole
purpose: it tells the engine the content is migrated when it is not, and moves
the breakage somewhere nothing points at it.

**`0.1.2_root-settings-schema.py` has no `migrate` command, deliberately.** The
tracker root is authored as JSONC with load-bearing comments explaining what
each vocabulary entry means, and a description is human-authored meaning a
script cannot invent — often the meaning already *is* the `//` comment beside
the value, and the job is to move it into the map. An automated rewrite would
strip or misplace those comments, so the script detects, prints the exact
replacement, and never touches the file.

**What the tag converter produces:** a callout in any form becomes a GFM alert
blockquote (`> [!NOTE]` / `[!TIP]` / `[!WARNING]` / `[!CAUTION]`, with
`info|note → NOTE`, `tip → TIP`, `warning → WARNING`, `danger → CAUTION`, and a
`title=` folded into the first bold body line); a collapsible becomes a native
`<details><summary>`; tabs are **flattened** into sequential `### <label>`
sections, because there is no native tab equivalent. Fenced code blocks, inline
code spans and frontmatter are skipped as mentions rather than usage.

## What's new

- **The version gate.** It runs inside `loadSiteConfig()`, the same place the
  `theme`-required rule already hard-throws, so it stops dev, build and preview
  alike. Content below the floor gets the migration instruction; content *above*
  the engine gets the other message — update the framework. There is no
  warnings-only mode: the stop is the feature.
- **Root-owned migrations.** `migration/<to-version>_<statement>.py` at the repo
  root, replacing the plugin's `migration/<date>_<name>.py`. Version order is
  execution order, and the authoring date moves into the docstring as
  provenance. The point of the move is that content format belongs to the
  engine, not to the plugin: a consumer who updates the framework now has
  exactly the migrations that engine needs, with no plugin-version skew.
- **A floor that means something specific.** `MIN_CONTENT_VERSION` is "the
  oldest content version that still *works* unmigrated", not "the newest
  migration available". A good-to-have migration leaves it alone and old trees
  migrate opportunistically; a breaking change raises it. Raise it needlessly
  and you force pointless migrations; forget it on a breaking change and old
  content loads silently wrong.
- **GFM alert blockquotes render** — `> [!NOTE]`, `[!TIP]`, `[!IMPORTANT]`,
  `[!WARNING]`, `[!CAUTION]` — in all three content types and in the editor
  preview, with theme-contract CSS. This is the native replacement the callout
  converter targets, and it shipped before the documentation described it.
- **The tracker Guide modal**, on the issues index. It explains a tracker to a
  cold reader: the seven statuses and four categories rendered from the code
  constants with their colours, an explicit fixed-versus-editable split, and
  every priority, component and label listed with its description — which is
  what the new `descriptions` requirement exists to supply.
- **`check legacy-tags`** — detects retired `:::` and `<tag>` syntax in any
  content root and names the native replacement, frontmatter-, fence- and
  inline-code-aware. It shipped here as `docs-guide check legacy-tags`.
- **Native markdown is the whole authoring story.** The reason is recorded in
  the tracker: AI authors write native markdown reliably and mass-produce errors
  in custom syntaxes. The trigger was a consumer incident — both skills
  documented a `:::callout{…}` syntax, 24 migration agents followed it in good
  faith across 45 files, and the framework had no `:::` parser at all.

## Fixed

- **A partial status-colour override dropped the other six defaults.** The
  loader now merges overrides onto the default palette instead of replacing it,
  so setting one colour no longer blanks the rest.
- **An unquoted `date:` in frontmatter was thrown away.** YAML parses
  `date: 2026-07-03` into a JS `Date`, and the comment reader accepted only
  `typeof fm.date === 'string'` — so the date silently became null and the
  comment rendered without one. Agent-log entries passed the raw `Date` through
  unnormalised. Both now go through one formatter, which uses `toISOString` on
  purpose: formatting in local time would shift the day in UTC-negative zones.

## Notes

- **The contract launched at `0.7.0` and was re-anchored to `0.1.2` thirty
  minutes later**, on the same day, by Sid — the beta scale starts low, and
  `0.7.0` was an informal "v0.7 lifecycle" number that had leaked out of the
  plugin's own versioning. The three migration scripts were renamed in the same
  pass (`0.5.0` → `0.1.0`, `0.6.0` → `0.1.1`, `0.7.0` → `0.1.2`), and
  `plugin.json`, which had briefly been bumped to `0.7.0` for the same reason,
  was corrected back to `0.5.1`. Nothing was ever published at `0.7.0`.
- **The floor was set to `0.1.2` here, and the gate could not enforce it.**
  `compareFormatVersions` compared the first two places and discarded the third
  — and every migration this project had shipped moved only the third. Content
  declaring `0.1.0` therefore compared *equal* to a floor of `0.1.2` and passed.
  The only thing this gate ever caught was a tree with no `engine_version` at
  all. It was fixed in `0.2.0`, which is the first release whose floor means
  anything. In practical terms: `0.1.1`'s breaking value remap reached nobody
  through the gate.
- **Two scripts share the version `0.1.2`, so they have no defined order between
  them.** They are independent by construction rather than by luck — one reads
  the tracker-root settings file and prints, the other walks content files and
  rewrites; neither consumes a list the other produces.
- **The two root-settings facets were merged into one script on purpose.** They
  touch the same file, ship together, and are both detection-only, so splitting
  them would have meant two passes over one hand-edited file.
- **Three of the four scripts named their pre-rename filename in their own USAGE
  block** (`2026-06-22_done-to-state.py`, `2026-07-02_state-to-status.py`,
  `2026-07-03_root-settings-schema.py`), so copy-pasting from a docstring failed
  on a file-not-found. Only `0.1.2_legacy-custom-tags.py`, written after the
  rename, was self-consistent. All corrected in `0.2.0`, after this note
  surfaced them — an older checkout still carries the wrong names.
- **The CLI was called `docs-guide` at this point**, and was renamed `agent-ks`
  on 2026-07-08 — inside the `0.1.2` → `0.2.0` window. The upgrade block above
  uses the current name, because that is what anyone reading this now has
  installed.
- **Could not be determined:** how many consumer trees existed at this point and
  therefore what the real blast radius of the mandatory `engine_version`
  declaration was. The history records one consumer project by its symptoms —
  the 45 files of `:::callout` syntax that triggered the native-markdown
  decision — but not who ran the migration or what it cost them.
