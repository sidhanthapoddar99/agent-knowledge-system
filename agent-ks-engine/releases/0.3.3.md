# 0.3.3 — `./start update` checks for a new version when you ask, and tells you why when it cannot

The automatic update check runs at most once every 6 hours. Inside that window it says
nothing at all, so a checkout one commit behind looks the same as a checkout that is
current. **`./start update` is the way out.** It checks now, offers the same
fast-forward pull, and names the reason when it cannot update.

**No content migration. `MIN_CONTENT_VERSION` stays at `0.2.0`.** Nothing on disk needs
changing — set `engine_version: "0.3.3"` in `site.yaml` when you upgrade.

Plugin: **`agent-ks` 0.8.5** — unchanged this release.

**Engine `0.3.3` · floor `0.2.0` · plugin `0.8.5`** — released 2026-08-10, tag `v0.3.3`.

## Upgrade

No migration scripts. The whole chain is:

```bash
git pull
./start doctor          # full build — confirms nothing broke
# then, in site.yaml:
#   engine_version: "0.3.3"
```

Set `engine_version` last, as always.

## What's new

### `./start update`

```bash
./start update
```

It looks at the git remote and offers the pull. Three things separate it from the
automatic check that runs on `dev`, `build`, `preview` and `doctor`:

- **It ignores the 6-hour interval.** You asked, so it checks.
- **It ignores `START_SKIP_UPDATE_CHECK=1`.** A command you typed is a stronger signal
  than a setting in your environment. The variable still governs the automatic check.
- **It starts nothing and builds nothing.** No dependency install, no version precheck,
  no server. Whether a newer version exists is a question about git, and the answer
  should not depend on whether this checkout can build today.

### It says why it cannot update

The automatic check stays quiet in these cases, because it runs in front of a dev server
and must not become chatter. `./start update` speaks:

| What it finds | What it prints |
|---|---|
| No git checkout | `not a git checkout — nothing to update from` |
| Detached HEAD, or no remote branch | `this branch tracks no upstream …` |
| Edited files in the checkout | `working tree has uncommitted changes — skipping update check` |
| No network | `fetch failed (offline?) — skipping update check` |
| Your branch moved too | `local branch has diverged … — resolve manually before pulling` |
| Nothing new | `up to date` |
| New commits | The count, then `pull now? [Y/n]` |

**The symptom this fixes:** you know a release shipped, you run `./start`, and nothing
happens. Before, that could mean four different things — throttled, no terminal, no
upstream branch, or a dirty tree — and all four looked identical, because all four
printed nothing. A throttle you cannot see is a throttle you cannot tell apart from a
bug.

### The automatic check no longer pulls under an unattended terminal

When there is no interactive terminal and an update exists, the check now reports the
count and stops, instead of returning silently before the fetch. Nothing is pulled
without someone to answer the prompt.

## Notes

- **The 6-hour throttle is unchanged.** `START_UPDATE_INTERVAL_HOURS` still tunes it and
  `0` still means every run. The fetch costs about 2.7 s, against a 2.4 s dev start, and
  that is the whole reason the throttle exists on a command typed ~20 times a day.
- **Known gap, not fixed here.** If the framework folder has no `.git` of its own — a zip
  download, or a copy vendored into your own repo — git walks upward and the check finds
  **your project's** repo instead. It will then offer to pull that. Clone the framework
  as documented and this cannot happen.
- **Z, not Y.** No content format moved.
