# 0.1.0 — state: becomes the only lifecycle field a subtask has

The boolean `done:` field is gone from subtask frontmatter. `state:` was already
the field the loader trusted; `done:` was a holdover it fell back to, and the
completion flag it exposed was re-derived from `state:` anyway. Removing it also
served as the first exercise of a new **migration-script convention** — one
stdlib-Python script per format change, carrying a detect pass, a `--dry-run`,
and an idempotent migrate.

**This release forces action** on any tree that still marks subtasks complete
with `done:` alone: the fallback that read them is gone, so they come back as
open.

**Engine `0.1.0` · floor n/a · plugin `0.2.1`** — released 2026-06-22, tag `v0.1.0`.

> **Reconstructed from git history on 2026-08-03.** No note was written and no
> tag was cut at the time, and `ENGINE_VERSION` did not exist yet — see Notes

## Breaking changes

| What changed | The symptom if you skip it | Fix |
|---|---|---|
| **`done:` retired from subtask frontmatter.** The loader's `state:`-missing → `done: true` → `closed` fallback is deleted; `state:` (defaulting to `open`) is the only input | A subtask marked complete with `done: true` and no `state:` line **renders as open** — it leaves the closed bucket, counts against its issue's subtask progress, and shows the open badge. Nothing errors; the page just says the wrong thing | `migration/0.1.0_done-to-state.py` |
| **The validator no longer accepts `done:`** — it is off the known-subtask-key list and out of the "no state" warning | Two lines per affected file from the issues check: `no state: — defaults to open`, plus an unknown-key drift warning naming `done` | same script |
| **`set-state` stopped writing `done:`** alongside `state:` | Anything still reading `done:` sees a value frozen at whatever it was before the upgrade — it no longer tracks flips, so it drifts silently rather than failing | same script (which removes the field entirely) |
| **The loader stopped exposing `done` on a subtask** (`IssueSubtask.done`) | A custom issues layout reading `subtask.done` gets `undefined`, so every subtask reads as incomplete. No bundled layout read it — this was checked by grep before the field was dropped | no script — derive completion from the status field instead |

## Upgrade

The script takes a path: a single `.md` file, one issue folder, or a whole
tracker. From the framework root:

```bash
python3 migration/0.1.0_done-to-state.py detect  <content-root>
python3 migration/0.1.0_done-to-state.py locate  <content-root>
python3 migration/0.1.0_done-to-state.py migrate <content-root> --dry-run
python3 migration/0.1.0_done-to-state.py migrate <content-root>

# idempotency check — expect 0
python3 migration/0.1.0_done-to-state.py detect  <content-root>
```

There is no `site.yaml` step here. `engine_version` does not exist until
**0.1.2**, which is where the version gate itself ships — so nothing on disk
records that a tree has reached 0.1.0. In practice nobody upgrades *to* this
version: it is the first link of a chain that ends at the current engine, and
the version to declare is the one at the end of that chain.

The mapping the script applies: `done: true` → ensure `state: closed`,
`done: false` → ensure `state: open`, and where a `state:` line already exists
`state` wins and the `done:` line is simply dropped. In every case `done:` is
removed. It rewrites frontmatter line by line, so key order, blank lines and the
body survive byte-for-byte.

## What's new

- **One lifecycle field on subtasks** — `state:`, with the four values
  `open | review | closed | cancelled`. The editor's save path had already been
  canonicalising to it; now the loader, the validator and the CLI agree.
- **The `migration/` convention** — the pattern every later format change
  follows. Stdlib Python because these are one-off runs rather than part of the
  live validator path; the module docstring is the source of truth for running
  the script; each one ships a detect pass that reports where and how much
  before anything is written, a `--dry-run`, and a migrate that is safe to
  re-run.

## Notes

- **The version number was assigned retroactively**, on 2026-07-03, when the
  engine↔content version contract was designed. `ENGINE_VERSION` did not exist
  on 2026-06-22 and this change shipped under no version at all — the script was
  originally `2026-06-22_done-to-state.py` inside the plugin. It was renamed
  `0.5.0_…` and then `0.1.0_…` the same day the contract landed. The rationale
  is recorded in the tracker, in the versioning issue's design note under
  *Re-anchor (2026-07-03)*.
- **This note is scoped to the format change the version names, not to a release
  window.** 0.1.0 is the oldest version the contract can name, so its "window"
  would reach back to the project's first commit. Everything that existed before
  2026-06-22 is simply the engine as it was; there is no earlier version to
  diff it against.
- **The script's own USAGE block named the file `2026-06-22_done-to-state.py`**
  — its pre-rename name — so copy-pasting from the docstring failed on a
  file-not-found. Corrected in `0.2.0`, after this note surfaced it. An older
  checkout still has the wrong name; use the `0.1.0_` name it ships under.
- **The CLI was a set of flat `docs-*` shims at this point** (`docs-set-state`,
  `docs-check-section`, …). The single `docs-guide` dispatcher arrived the next
  day and was renamed `agent-ks` on 2026-07-08 — so verify with whatever your
  installed plugin provides, not the command names in contemporary documents.
- **Could not be determined:** whether any consumer outside this repo was
  running the engine at this point, and therefore whether the `done:` removal
  ever broke anyone's tree in practice. The repo's own content was migrated in
  the same commit that removed the fallback.
